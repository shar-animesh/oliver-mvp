0Executive position

Oliver should become a stateful lifecycle system, but the safe route is an incremental modular architecture—not a wholesale rewrite and not a mesh of seventeen independent model calls.

Architecture decision. Keep PostgreSQL as the system of record, preserve the current email and dashboard surfaces, introduce one canonical initiative aggregate, and separate AI judgement from deterministic control. Begin with two reasoning agents—Assessment and Coach. Add Portfolio Intelligence after lifecycle data is trustworthy, then add Scout as a governed candidate-discovery capability.
AI reasoning

Interpret

Understand evidence, explain gaps, identify portfolio patterns, and draft communication.

Deterministic control

Decide

Calculate official scores, validate transitions, enforce permissions, schedule work, and record delivery.

Canonical state

Remember

Store one initiative identity, versioned evidence, assessments, decisions, and lifecycle history.

Target outcome: every idea can be reassessed as evidence changes, moved through DI1–DI5 under explicit authority rules, observed as part of a portfolio, and audited from inbound message to final lifecycle decision.

2Architecture drivers and principles

The design is governed by lifecycle integrity, explainability and operational safety—not by the number of agents.

DriverRequired architectural responseEvidence of success
Complete reassessmentBuild every assessment from a versioned evidence snapshot containing relevant historical and new evidence.The same evidence version always reproduces the same deterministic score inputs.
Safe lifecycle movementPut transition policy in StageMaster code; require recorded human authority for irreversible states.No model response can directly mutate lifecycle state.
No accidental duplicationUse provider message IDs, content hashes, unique constraints and an outbox; distinguish history from redundant copies.Retries create no duplicate message, assessment, event or delivery.
Model portabilityAll model and embedding names come from environment configuration behind one provider boundary.Provider/model changes require configuration, not domain-code edits.
Operational trustPersist correlation, prompt/rubric/model versions, fallback state, latency and delivery outcome.An admin can explain what happened and retry safely.
Least privilegeSeparate interactive Entra roles, Logic App managed identity and database roles.Each caller can access only its required API and data operations.
Principle: the model may interpret evidence and recommend; versioned code owns scoring, permissions and lifecycle state. This boundary is the foundation for reliable agentic behaviour.

6Runtime behaviour

Three flows define the target behaviour: evidence-led reassessment, governed lifecycle movement and proactive candidate discovery.

A. New idea or reassessment

1
Intake
Validate caller, normalize the email, enforce message-ID idempotency and store the original message once.
2
Registrar
Resolve the canonical initiative; create one only when the message represents a genuinely new idea.
3
Evidence service
Extract approved attachments, classify evidence and create an immutable evidence version referencing source records.
4
Assessment Agent
Read the evidence snapshot, current stage and prior assessment; return typed findings, gaps, citations and confidence.
5
Scoring service
Apply the versioned rubric and stage weights to produce the official score and recommendation.
6
StageMaster
Validate the recommendation against the current state, hold status and human-authority rules.
7
Idea Coach
Compose a grounded response from the approved result; it cannot alter score, stage or decision.
8
Herald / Auditor
Create one outbound delivery request, record the complete trace, then accept the Logic App delivery callback.

B. Governed lifecycle movement

1
StageMaster
Creates a transition proposal from the canonical assessment and current lifecycle version.
2
Policy
Automatically applies an allowed DI1–DI4 move, or routes DI5 / No-Go / Retire / override to the approval queue.
3
Admin
Approves, rejects or requests evidence with a mandatory reason; the decision is optimistic-lock protected.
4
Auditor
Appends actor, before/after state, evidence and assessment versions, reason and correlation ID.

C. Scout candidate discovery

1
Connector
Reads only an approved source scope under the source owner's access and retention policy.
2
Scout
Identifies a problem, plausible value/data signal and possible owner; returns source references and confidence.
3
Registrar search
Checks exact hashes and semantic similarity against initiatives and existing candidates.
4
Admin review
Accepts as a draft, merges with an initiative or rejects with a reason. No submitter is contacted automatically.

8Lifecycle governance

The DI stage is authoritative domain state. A model may recommend a stage; StageMaster and the applicable human authority decide whether state changes.

StageOfficial nameArchitectural meaningMovement rule
DI1ConceptProblem, intended outcome and initial ownership are being established.May progress automatically when policy and evidence thresholds pass.
DI2PilotPilot scope, data access, sponsor and measurable success criteria are credible.May progress automatically unless held or routed to review.
DI3TestTechnical and business hypotheses are being validated with evidence.May progress automatically unless held or routed to review.
DI4ImplementProduction readiness, operations, controls and ownership are evidenced.Proposal to DI5 always requires human approval.
DI5ScaleThe initiative is deployed, monitored and delivering measured value.Terminal scale state; future changes are monitor/value events, not “path to DI5”.

Automatic authority

  • Valid forward movement within DI1–DI4
  • Only when confidence, evidence and policy gates pass
  • Never while the initiative is on HOLD
  • Every change remains reversible through a governed proposal

Human authority

  • DI5 Scale
  • No-Go and Retire
  • Manual stage override or rollback
  • Low-confidence / policy-exception decisions
  • Hold and resume actions with a reason

HOLD semantics: stop automatic transitions, reminders and escalation. Continue accepting and storing evidence. Permit an authorized admin to run a manual reassessment without silently resuming the initiative.

10Integration and resilience architecture

Public contracts remain small and stable. Internal side effects use an outbox so persistence and event publication cannot disagree.

Contract groupPurposeReliability rule
Email intakeReceive normalized message, participants and attachment references.Unique provider message ID; acknowledge only after durable acceptance.
Delivery resultRecord Logic App accepted, sent or failed outcome.Idempotent by delivery attempt ID; failures remain retryable and visible.
Initiative queryPortfolio list, initiative detail, evidence and timeline.Read projections derive from canonical records; no hidden business rules in the UI.
Lifecycle commandsHold, resume, reassess and decide a transition proposal.Role check, expected lifecycle version and mandatory reason.
SandboxRun the same assessment contracts against test input.Explicit sandbox partition; never mutates live state or sends email.
Scout reviewList, accept, merge or reject candidates.Human-reviewed command with source citation and duplicate check.

Event envelope

Every internal event carries event_id, event_type, schema_version, occurred_at, initiative_id, correlation_id, producer and a minimal payload or record reference. Initial event types are message.received, evidence.versioned, assessment.completed, transition.proposed, transition.applied, delivery.updated and scout.candidate_created.

Model failure

Validate structured output; retry transient failures; fall back only where an evaluated fallback exists. Never persist invented score/stage data.

Workflow failure

Persist processing state and error category. Resume from the failed step using the same idempotency and correlation keys.

Delivery failure

Keep the assessment committed, mark delivery failed, retry with backoff and surface the attempt in Operations.

Each increment leaves Oliver deployable and creates the foundation for the next. The order is architectural: reliable state before autonomy.

ChangeAssessment Agent returns typed evidence findings; deterministic code maps them to the versioned rubric; Coach receives only the approved result. Keep provider/model configuration in .env.
